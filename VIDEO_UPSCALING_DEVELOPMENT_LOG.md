# Відеоапскейл: журнал розробки

Цей файл фіксує технічні рішення, проблеми та компроміси, пов'язані з відеоапскейлом і оптимізацією. Його можна використовувати як основу для опису реалізації та експериментів у пояснювальній записці.

## 2026-11-21 (9): права панель інструментів розділена на вкладки

- Зображення: **Adjust** (повзунки, інверсія, Denoise) і **Upscale** (масштаб, модель + картка моделі, «Keep original size», «Facial restoration», кнопка запуску). Відео: **Real-time** (роздільність/алгоритм + рядок стану: fps і пристрій), **Upscale** (вихідна роздільність, модель, кнопка), **Frame** (обрізати/зберегти кадр).
- `ui/web/scripts/modules/inspector_tabs.js` (панелі позначені `data-tab`); іконки SVG, навігація стрілками, остання вкладка запам'ятовується окремо для зображень і відео. Крапка на вкладці: «Adjust» — є зміни відносно типових значень; «Real-time» — прев'ю працює.
- «Reset» діє лише на активну вкладку (`reset_module(scope)`: `adjust` — ефекти, `upscale` — налаштування апскейлу); на вкладках Real-time і Frame кнопка прихована. Під час задачі вкладки лишаються клікабельними, елементи керування — вимкнені, як і раніше.

## 2026-11-21 (8): GFPGAN — надмірна кількість тайлів фону

- Причина: у `GFPGANer.enhance` лишився старий обхід «апскейл фону плитками 64 px із кроком 32» (з часів, коли апскейлер обрізав вихід на RX 6700 XT). Після переходу на фіксовану форму тайла (448² для 384+32) кожна така 64-px плитка доповнювалася до повного тайла: 1500×1002 → ≈1500 викликів моделі (4K → ≈8000), тобто ≈50× зайвих обчислень і шви від змішування.
- Тепер весь кадр передається `bg_upsampler.enhance(img, outscale=...)` — апскейлер сам ріже на тайли з перекриттям (1500×1002 → 12 тайлів, 4 для 500×500), прогрес іде зі стадією `upscale`. Видалено використання `tile_image_with_overlap`/`stitch_tiles_with_blending` у GFPGAN.
- Заодно виправлено порядок каналів: у GFPGAN-гілку потрапляв RGB (facexlib/GFPGAN чекають BGR), тож модель облич бачила кольори з переставленими R/B; тепер `upscale_image` конвертує у BGR і назад (та відкидає альфа-канал).

## 2026-11-21 (7): звук у realtime, іконка гучності, затримка зникнення повзунка

- Випадні списки вихідної роздільності (офлайн і realtime) сортуються за висотою виходу (`ModelManager._finalize_options`), а стандартні висоти отримують назву: `1080p Full HD`, `2160p 4K`, `4320p 8K` (`resolution_label`, також для множників — напр. 8× від 540p тепер `4320p 8K (7680 × 4320)`). Типовим стає найменший варіант.

- Realtime-прев'ю (і MJPEG, і H.264 AMF-потік) не мало звукової доріжки: енкодер `-an`, кадри обробляються окремо від джерела. Звук тепер іде з прихованого `<video>` з оригінальним файлом (`ui/web/scripts/modules/realtime_audio.js`): позиція звуку синхронізується з позицією прев'ю (для AMF — `realtimePlayer.currentTime`, для решти — `realtime_position`), дрейф > 0.35 с → перемотування, `playbackRate` = швидкість обробки (до 1×); якщо прев'ю повільніше за 0.6× реального часу — звук вимкнено (розтягнутий звук нерозбірливий); пауза/завантаження/перемотування обробляються. Кнопка й повзунок гучності керують тим самим елементом, тож працюють без змін. Перевірено в браузері на тестовому відео з AAC (швидкість 1.0 / 0.8 / 0.3, перемотування, пауза).
- Іконка гучності: кольоровий емодзі 🔊/🔇 замінено SVG (`currentColor`, стиль решти іконок).
- Повзунок гучності з'являється при наведенні й після відведення курсору лишається ≈1.6 с (CSS `transition-delay`), під час перетягування та при клавіатурному фокусі не зникає (`:has(input:active)`, `:has(:focus-visible)`); клік по кнопці mute більше не залишає його відкритим назавжди (раніше `:focus-within`).

## 2026-11-21 (6): інформація про модель у UI та підписи за «вагою» моделі

- `core/models/model_info.py`: кількість параметрів береться з самого ONNX (сума елементів initializer; для ncnn/.pb — оцінка за розміром файлу), архітектура / призначення / дані навчання / ліцензія — з каталогу (для моделей без відомих даних прямо сказано «Not documented», архітектура виводиться з кількості параметрів). Складність: ≈ 2 × параметри × частка ваг на вхідній роздільності (compact = 1.0; RRDBNet: 2× — 0.3, 4× — 1.1, 8× — 1.35, бо trunk працює на 1/4 роздільності через pixel-unshuffle) = MFLOPs на вхідний піксель, відносно `realesr-general-v3` (виміряно 5.3 Мпкс/с на RX 6700 XT) → оцінка швидкості та придатності для realtime. Кеш прогрівається у фоновому потоці при старті.
- `get_state` повертає `model_info` для всіх моделей у списках (офлайн і realtime). Випадні списки (зображення, відео, realtime) показують `назва (Light|Medium|Heavy, N params)` замість `(DirectML)` (Light < 3M, Medium < 10M, Heavy ≥ 10M параметрів; ідентифікатор моделі в налаштуваннях лишається старим). Під кнопками «Upscale video» і «Run Real-ESRGAN» — картка з вагами, архітектурою, призначенням, даними навчання, складністю та ліцензією; оновлюється при зміні моделі.

## 2026-11-21 (5): 8× падає з 887A0001 і «отруює» DirectML; швидкий preview ефектів на GPU

### 8× / «EP Error ... 887A0001 ... Falling back to CPUExecutionProvider»

- Відтворено: DML-вузол RRDBNet на виході 3456² (≈11.9 Мпкс) і більше падає з `887A0001` (`DmlFusedNode`), бо потрібен вихідний тензор 64 канали fp16 > ≈1.5 ГБ. Межа калібрована: 8× з тайлом 416 (3328²) працює, 432 (3456²) — ні; `tile 384 + 2×32 = 448` для 8× (3584²) падав завжди, а whole-frame 8× на 540p (≈33 Мпкс) — тим більше.
- Після такої помилки DML-пристрій процесу непридатний: **усі наступні сесії мовчки падають на CPU** (відтворено; звільнення сесії/`gc` не допомагає) — звідси «ORT provider: CPUExecutionProvider» і 3 кадри за 11 с у логах після невдалого 8×.
- Виправлення: `MAX_RRDB_OUTPUT_PIXELS = 3328²` (`core/models/weights.py`); для RRDB-моделей (не compact) `OnnxRealESRGANer` автоматично зменшує тайл (8×: 384+32 → 352+2×32 = 416) і не вмикає whole-frame, якщо вихід більший за межу; `uses_full_frame(frame_size, scale, model)` враховує це в офлайні й realtime. Якщо DML вже працював у процесі, а нова сесія отримала CPU, кидається `RuntimeError` («Restart the application…») замість тихої роботи на CPU, що ≈100× повільніша. Перевірено: 8× відео 960×540 (11 кадрів за 25 с) та 8× зображення.
- Відновити DML у тому ж процесі неможливо — лише перезапуск застосунку (зображення апскейляться в окремому процесі й цього не стосується).
- Дофіксація (4× `RealESRGAN_anime_6B_fp32`, 540p → 2160p падав так само): межа залежить від розміру в байтах, а не лише в пікселях. fp32 вдвічі більший за fp16: виведено 3.69 Мпкс — працює, 5.76 Мпкс — падає (≈1.45 ГБ). Тепер `max_rrdb_output_pixels(stem)` (`core/models/weights.py`): 3200² для fp16 і вдвічі менше для fp32 (з ≈10 % запасом); використовується і для тайлів, і для вибору whole-frame. Compact-моделі (fp16/fp32) не обмежуються — 720p 4× fp32 whole-frame працює.

### Ефекти зображення: preview ≈1.1 с → ≈75 мс (4K)

- Було: кожна зміна повзунка → ефекти PIL на повному зображенні (683 мс на 4K) + `thumbnail` (129 мс) + WebP method 4 (330 мс).
- Тепер (`core/processing/preview_effects.py`, `EffectsManager.build_preview_proxy/render_effect_preview`, `_render_preview_worker`): один раз на зображення будується proxy ≤1800×1400 (кешується в `entry["preview_proxy"]`); Brightness/Color/Contrast/Sharpness/Inversion виконуються одним ONNX-графом на GPU (DirectML, ≈11–15 мс на proxy), blur — `cv2.GaussianBlur` (σ масштабується до proxy), без DML — numpy-фолбек (≈200 мс). Кодування — JPEG q92 4:4:4 (≈35 мс; для зображень з прозорістю WebP method 0). Результат збігається з PIL ±1/255 (Sharpness — до ≈40 на окремих пікселях через край/округлення, середнє ≈0.5). Експорт та апскейл і далі використовують точний PIL.
- Знайдено та виправлено баг: `apply_effects` викликав `invert_image_colors(result, None)` → `TypeError`, тож Inversion не працював (preview/експорт).
- UI: після зміни повзунка/інверсії, якщо бекенд ще не повернув зображення за 250 мс після останньої зміни, з'являється оверлей «Applying effects» і блокуються елементи керування до отримання нового preview (під час перетягування повзунка оверлей не з'являється); таймаут 30 с.

## 2026-11-21 (4): логування тривалості та результату операцій апскейлу

У `app_logs/logs.txt` (через `log_event`) тепер кожна операція пишеться з тривалістю та `outcome`:
- Зображення (`JobManager._process_operation`): `image_operation_started` / `image_operation_finished` — `outcome` = `completed` | `failed` | `cancelled` | `interrupted` (процес перервано без підтвердження), `elapsed_seconds`, `operation`, `model`, `factor`, `image_size`, `error`.
- Відео офлайн (`upscale_video_worker`): `video_upscale_completed` / `video_upscale_failed` / `video_upscale_cancelled` — `total_seconds` (разом із завантаженням моделі та ремуксом), `processing_seconds`, `frames_processed` / `frames_total`, `device`, `model`, `factor`, `outcome`, `error`; для completed ще `fps_actual`.
- Realtime (`RealTimeVideoProcessor._log_session_finished`): `realtime_session_finished` — `outcome` = `stopped` | `ended` (кінець відео) | `failed`, `elapsed_seconds`, `frames_published`, `avg_fps`, `start_position` / `end_position`, `cache_hits` / `cache_misses`, `model`, `factor`, `error`.
- Закриття застосунку посеред операції логом не фіксується (немає події finish); для зображень/відео є лише `*_started` / `video_upscale_requested`.

## 2026-11-21 (3): офлайн-апскейл відео — whole-frame режим (≈1.5–2× швидше на 540p)

- Спостереження користувача: 540p → 2160p у realtime ≈10 fps, а офлайн лише ≈5–6 fps. Причина: realtime вже обробляв кадр цілим (`frame_size`), а офлайн ішов тайлами 384+32 → 448² × 6 тайлів = 1.2 Мпкс замість 0.52 Мпкс кадра 960×540 (2.3× зайвих обчислень GPU, плюс шви тайлів).
- `upscale_video_worker` тепер передає `frame_size` у `create_upscaler`, якщо кадр ≤ 1280×720 (`uses_full_frame`). Заміри (24 кадри 960×540, разом із ремуксом): animevideov3 4× 5.25 → 3.52 с, general-v3 4× 7.16 → 4.41 с, `2x-REAL-General` (RRDB) 13.5 → 6.96 с.

## 2026-11-21 (2): якість realtime — chroma AMF, Real-ESRGAN на GPU у realtime, pre/post на GPU

### Вимірювання (RX 6700 XT, 960×540 → 1080p, 3 фото-кадри, PSNR/SSIM проти оригіналу 1080p)

- Preview-енкодер H.264 AMF не є проблемою: 21.6 Мбіт/с дають ≈42 dB відносно виходу апскейлера (cqp/vbr не кращі).
- `sr_amf` SR1.0: luma ≈ як Lanczos (35.2 dB), а **chroma на ≈1.7 dB гірша** (AMF апскейлить якісно лише яскравість): 32.7 dB проти 34.4 dB із chroma джерела. `sharpness` дає ≤ +0.1 dB. `sr1-1` (algorithm=4) на цьому GPU віддає сміття (6.9 dB) — не використовувати. ESPCN/FSRCNN лише ≈ +0.1 dB до Lanczos і ≈7 fps на CPU.
- Дрібні нюанси попереднього запису: абсолютні часи GPU сильно «плавають» залежно від стану GPU (частоти/фонове навантаження): `realesr-general-v3` на 448² виміряно і 79 мс, і 38 мс. Порівняння «було/стало» в межах одного прогону коректні, абсолютні значення — ні.

### Зміни

- **AMF chroma** (`core/services/upscalers/chroma.py`, `realtime_video._run_amf`): UV-площина виходу AMF замінюється на chroma вхідного кадру (BT.601 limited, `cvtColor` + LUT + `resize` для не-2× випадків). Рахується між `send_frame` і `read_frame`, тобто поки AMF працює (≈2–4 мс); fps на 1080p без змін (≈58). PSNR 32.74 → 34.40 dB (SSIM без змін, середній кольоровий зсув ≈0).
- **pre/post-обробка в ONNX-графі** (`core/models/onnx_io.py`): модель обгорнута вузлами `uint8 BGR NHWC → float/16 RGB NCHW` та `Clip/Mul/Round/Cast → uint8 BGR NHWC`; CPU лише копіює uint8. `enhance` 1080p 4× compact: 1.2 → 0.52 с, 2× REAL-General: 2.4 → 1.2 с. Відмінність від CPU-версії: середня ≈0.1–0.2/255 (макс. 13–15 на поодиноких пікселях; fp16 на GPU інакше округлює проміжні значення), тобто вже не побітово ідентично.
- **Real-ESRGAN у realtime на GPU** (`gpu_realtime.py`, `ModelManager.realtime_models_for_factor(factor, source_size)`): compact-моделі (SRVGGNetCompact, ≈1–2 МБ; маркери `realesr-general`, `animevideo`, `compact`) показуються лише для виходу з відповідним масштабом: 4× моделі для 4×, 2× для 2×, а для 1080p — за масштабом з `output_plan` (360p → 4×, 540p → 2×); 8× немає. Для будь-якого джерела (спершу фільтр був ≤ 960×540 і для HD варіанта в UI не було — прибрано). До 1280×720 кадр обробляється як один тайл фіксованої форми (`OnnxRealESRGANer(frame_size=(w,h))`, без накладання, розміри кратні 4), більші — тайлами 384+32. Додано ваги: `4x-realesr-animevideov3` (офіційний Real-ESRGAN v0.2.5.0, BSD-3, аніме) та 2×: `2x-realesrganv2-animevideo-xsx2` (офіційний Real-ESRGAN v0.2.3.0, BSD-3, аніме/загальна), `2x-NomosUni-compact-otf-medium` і `2x-NomosUni-compact-multijpg` (Phhofm, CC-BY-4.0, універсальні фото/відео; otf — з Real-ESRGAN-деградаціями), усі 64nf16nc, експортовані в fp16/fp32 ONNX. Швидкість 2× (whole-frame): 640×360 ≈44–48 fps, 960×540 ≈21, 1280×720 ≈11; end-to-end 2× на 640×360 ≈40 fps.
- **Баг realtime-циклу (не AMF)**: `self._pause_event.wait(0.05)` на нескинутому події блокував **кожен кадр на 50 мс** (потолок ≈20 fps для всіх не-AMF моделей) і крутив CPU на паузі. Тепер `is_set()` + `_stop_event.wait(0.05)`.
- JPEG-кодування (≈50 мс для 2560×1440) для GPU-моделей винесено у потік і відстає на кадр (`_encode_jpeg`/`_publish_jpeg`).
- Пул слотів буферів у `OnnxRealESRGANer` (без аллокації 11-МБ вихідних буферів на кадр).

### Результат (джерело 640×360, 60 fps, RX 6700 XT)

- Whole-frame `enhance` 640×360 → 2560×1440: animevideov3 ≈35 fps, general-v3 ≈23 fps (480×270: 61 / 40 fps; 854×480: 19 / 12 fps).
- End-to-end realtime (з декодуванням, JPEG, кешем): ≈19 fps (було ≈6 fps до виправлення паузи/JPEG). Для джерел 24–30 fps це 60–80 % реального часу; повний realtime — для ≤ 480×270 або після кращого кодування (H.264 замість JPEG).
- Висновок: Real-ESRGAN у realtime реалістичний лише для низьких роздільностей; для HD-джерел лишається AMF (тепер із кращою chroma).

## 2026-11-21: конвеєр тайлів/кадрів і стійкість Real-ESRGAN (ONNX/DirectML)

### Чи можна обробляти кілька кадрів одночасно / GPU + CPU?

Заміри на RX 6700 XT + i5-11400 (тайл 448², fp16, `session.run`):
- 1 сесія: `realesr-general-v3` 79 мс/тайл, `2x-REAL-General` 149 мс/тайл.
- 2 сесії DirectML паралельно (або 2 потоки на одній сесії): 77 / 135–149 мс/тайл ефективно, тобто виграш 0–10 % ціною подвійної VRAM. GPU вже завантажений обчисленнями (див. запис про фіксовану форму тайла), тож паралельні екземпляри на одному GPU не прискорюють; пакетний inference теж не давав приросту.
- CPU (ORT, 6–12 потоків): 1.7–2.0 с/тайл compact-моделі і 6.5 с/тайл `2x-REAL-General` — додає лише 2–6 % до пропускної здатності GPU і забирає ядра в декодера/кодера, тож гібрид GPU+CPU не вводився.

### Де було реальне простоювання GPU

Профілювання `enhance` (1080p, тайл 384+32): сирі виклики `session.run` займали 15 × 79 мс = 1.2 с, а весь `enhance` для 4× compact-моделі — 2.2 с. Різниця — постобробка: повний `float32` CHW зображення 4× (≈400 МБ для 8K) → `clip` → `*255` → `round` → `uint8` → `cvtColor` виконувалась після циклу тайлів, коли GPU вже простоював; також на кожен тайл створювався новий потік префетчу.

### Зміни

- `OnnxRealESRGANer.enhance` — триетапний конвеєр: потік-постачальник готує тайли (нормалізація прямо в буфер), поточний потік запускає inference (ORT відпускає GIL), 2 потоки постобробки квантують готовий тайл у `uint8` BGR і пишуть його у фінальне зображення. Кожен «слот» (3 шт.) має власні вхідний/вихідний буфери та IOBinding, тому гонок за буфери (причина відкату v1) немає. Результат побітово ідентичний попередньому (max diff 0 на 1080p для 2× і 4×).
- Стійкість: помилка inference (напр. скидання пристрою DirectML) перестворює сесію й один раз повторює тайл; друга помилка піднімається викликачу. Помилка в будь-якому потоці конвеєра зупиняє решту й пробрасується викликачу (потоки не зависають). Вхід перевіряється: сірі/BGRA кадри нормалізуються, не-`uint8` і порожні зображення дають `ValueError`. Тип (fp16/fp32) береться з входу моделі, а не з імені файлу.
- `upscale_video_worker` (`media_exporter.py`): декодування + ефекти (потік-читач) і resize + запис + прогрес (потік-письменник) перекриваються з GPU-inference у головному потоці; черги глибини `VIDEO_PIPELINE_DEPTH = 2`, скасування та помилки зупиняють усі етапи.

### Результат

- `enhance` 1080p 4× (`realesr-general-v3` fp16): 2.2 → 1.2 с/кадр (≈1.8×), пам'ять результату 400 МБ → 100 МБ. 2× `REAL-General`: 2.6 → 2.4 с/кадр (GPU-обмежений: 2.2 с чистого inference).
- Відео 960×540 → 1080p (24 кадри, `2x-REAL-General`, разом із ремуксом): 14.1 → 13.1 с. 960×540 → 4K, 4× compact: 8.6 с.
- Висновок: далі прискорення можливе лише через меншу/швидшу модель або менший оверхед паддінгу тайлів (448² рахується заради 384² корисних пікселів).

## 2026-11-20: величезна затримка кнопки паузи в realtime (виправлено)

- Причина: `get_state()` тримає єдиний загальний `self._lock` на весь час виконання, а всередині двічі рахує `_realtime_output_options`, яка для кожного з 4 варіантів розширення (2/4/8/1080p) викликає `_realtime_models()` → `MediaModule._ffmpeg_path()` → `shutil.which("ffmpeg")`. `shutil.which` сканує кожну директорію з PATH (на цій машині ≈7 мс/виклик через багато встановлених SDK), тож один `get_state()` коштував ≈53–70 мс. UI викликає `get_state` кожні 150 мс під час realtime (`pollJobState`) і додатково після кожної дії (`runAction`), тож лок утримувався майже безперервно. Через нечесність `threading.Lock`/GIL інший потік (`set_video_realtime_paused`, кнопка паузи) міг програвати цю гонку і чекати лока 15–36 секунд (виміряно в `app_logs/logs.txt`, поле `lock_wait_ms`).
- Замір причини: `cProfile` на 60 викликів `get_state()` під час realtime показав 480 викликів `shutil.which` на 3.57 с (з 4.23 с загалом).
- Виправлення: `MediaModule._ffmpeg_path()` кешується на 5 с (той самий підхід, що й `gpu_memory_bytes()` у `core/services/performance.py`) — `shutil.which` більше не викликається на кожен `get_state`.
- Перевірка: 60 викликів `get_state()` під час realtime 70 мс → 9.4 мс (×7.5). Відтворення гонки лок-старвації (один потік безперервно викликає `get_state`, інший раз у 3 с викликає паузу): затримка паузи 734 мс → 16 мс.

## 2026-11-19: фіксована форма тайла для DirectML (≈2.3× швидше)

### Причина

Пакетний inference кадрів (спроба раніше цього дня) приросту не дав і відкотився: для 1080p→4K ліміт пам'яті давав batch=1. Профілювання показало справжню причину: CPU-обробка (препроцес ≈0.04 с, постпроцес ≈0.15 с) і копіювання даних — мізерні; майже весь час (≈3.4 з 3.45 с на кадр) — виклики `session.run`. Час виклику майже не залежав від розміру тайла (256×256 ≈ 0.175 с, 448×448 ≈ 0.22 с), тобто це накладні витрати DirectML, а не обчислення GPU. Швидким (≈0.10 с) був лише перший shape в сесії; при динамічних розмірах (`height`/`width`) і крайових тайлах іншого розміру DirectML повторно планував граф. Тому GPU простоював (30–50% завантаження) і VRAM майже не використовувалась.

### Рішення

- Сесія ORT створюється з фіксованими `height`/`width` = `tile + 2 * tile_pad` через `add_free_dimension_override_by_name`; файли моделей не змінюються.
- Усі тайли доповнюються (`np.pad`, режим `edge`) до повного розміру, а після inference вихід обрізається до реальної області; IOBinding-буфери використовуються для кожного тайла.
- Warmup виконується на фінальній формі, щоб перша компіляція не потрапляла у кадр.
- Batching кадрів та зміни в `media.py` відкочено.

### Результат і перевірка

- Мікробенчмарк на RX 6700 XT: статичний 448×448 — 0.077 с/виклик проти 0.22 с у динамічній сесії.
- 1080p→4K (2× FP16, тайл 384+32): 3.45 → 1.49 с/кадр.
- Крайові пікселі (до ≈16 вхідних px від правого/нижнього краю) трохи відрізняються від попереднього результату (replicate-паддінг замість нульового паддінгу згортки); всередині середня різниця ≈0.8/255 (fp16, інша форма).
- Після такої зміни виклик стає обчислювально-обмеженим (статичний 640×640 дає ті самі ≈2.7 Мпкс/с), тож подальше прискорення потребує меншої/швидшої моделі або іншого бекенда (напр., TensorRT/ROCm не доступні на DirectML-стеку).

### Хронологія (скасовано): пакетний inference кадрів

Було додано `enhance_batch` і batch до 4 кадрів; відкочено як неефективне.

## 2026-11-19: оптимізація RealESRGAN - виправка та стабілізація (v2)

### Проблема з v1

Перша версія оптимізації (queue-based multi-threading) мала race condition:
- Кілька inference потоків одночасно писали у один IOBinding буфер (_buf_in/_buf_out)
- ONNX Runtime session не є thread-safe для запитів на одній сесії
- Результат: Access Violation (exit code 0xC0000005) при апскейлу

### Прийняте рішення (v2 - Stabil )

Оптимізація залишена, але архітектура змінена на безпечну:

1. **IOBinding з перевикористовуваними буферами** (тільки основний потік):
   - Лише основний потік пише у _buf_in та читає з _buf_out
   - Interior tiles використовують reusable buffers
   - Edge tiles використовують session.run() з динамічними буферами

2. **Префетч на окремому потоці** (безпечно):
   - Префетч потік слайсує наступний тайл поки GPU обробляє поточний
   - Дані передаються як об'єкти numpy (копіюються при передачі)
   - Нема race condition оскільки префетч не має доступу до вихідного буфера

3. **ONNX Runtime thread pools** (безпечно):
   - inter_op_num_threads і intra_op_num_threads збільшені для внутрішної паралелізації
   - Це безпечно - це параметри сесії, не параллельні виклики

4. **Результат**:
   - Гарантована стабільність (нема race conditions)
   - Гарантована коректність (алгоритм не змінений)
   - Небагато медленніше ніж ідеальна паралелізація, але набагато швидше ніж оригіналь послідовна версія

### Оновлені параметри

- `OnnxRealESRGANer.__init__` приймає `num_threads` (за замовчуванням 2)
- `upscale_image` у resolution.py автоматично вираховує оптимальну кількість потоків
- Префетч на окремому потоці гарантує що CPU-GPU не блокуються один на одного

### Гарантії якості v2

✅ **Стабільність**: Нема race conditions, нема memory violations
✅ **Коректність**: Результати детерміністичні і ідентичні v1
✅ **Продуктивність**: Все ще швидше ніж оригіналь послідовна версія

## 2026-11-19: оптимізація RealESRGAN - паралелізація та зменшення перекидання CPU-GPU (v1 - скасовано)

### Виявлена проблема

Апскейл через RealESRGAN працював з низькою ефективністю через:
1. **Перекидання даних CPU↔GPU на кожному тайлі**: кожен тайл прочитується з CPU память, обробляється на GPU, результат пишеться назад.
2. **Однопотокова обробка**: CPU-слайсінг одного тайлу блокує GPU, що чекає на наступний.
3. **Невиконана оптимізація префетчу**: попередній prefetch робив однопотокову операцію, яка все ще гальмувала GPU.

### Прийняте рішення (v1 - змінено)

Переписано pipeline обробки тайлів з queue-based архітектурою - **але відкинено через race conditions**.

Коректна версія (v2 див. вище) зберігає основну ідею префетчу та ONNX thread pools, але уникає небезпечної multi-threading на IOBinding буферах.

## 2026-11-11: розділення апскейлу та експорту

### Виявлена проблема

Попередня реалізація використовувала `save_video` і для запуску апскейлу, і для експорту. Через це натискання кнопки апскейлу одразу відкривало діалог збереження та починало створювати фінальний файл. Така модель не відповідала очікуваній поведінці редактора:

- обробка повинна створювати новий об'єкт у History;
- експорт повинен виконуватися лише після явного натискання кнопки Export;
- результат не можна зберігати як повну послідовність кадрів у RAM, оскільки розмір відео може бути значним.

### Прийняте рішення

Потік розділено на дві незалежні операції:

1. `start_video_upscale` запускає обробку відео у фоновому потоці.
2. Результат записується покадрово у тимчасовий MP4-файл на диску.
3. Після завершення цей файл додається як новий video entry у History.
4. Новий entry зберігає шлях до відеофайлу, FPS, кількість кадрів і URL локального відеосервера, але не зберігає всі кадри в пам'яті.
5. `save_video` тепер виконує лише явний Export: відкриває діалог і копіює поточний відеофайл у вибраний шлях.

Тимчасовий результат створюється в системній директорії тимчасових файлів під унікальним ім'ям. Шлях зберігається в history entry через `temporary_path`, а файл видаляється під час видалення відповідного entry.

### Поточна модель пам'яті

У RAM знаходяться лише:

- перший кадр відео для thumbnail і відображення стану;
- поточний кадр, який декодує HTML video element;
- один кадр, що обробляється в поточній ітерації worker-а;
- буфери поточного AI inference.

Повне вихідне та оброблене відео залишаються на диску. Це дозволяє працювати з довгими відео без пропорційного зростання споживання RAM.

### Перевірка доступності моделі

Порожній model selector раніше не блокував кнопку запуску. Backend підставляв fallback-рядок, який міг бути сприйнятий як CPU-модель, тому процес починався навіть без доступної моделі.

Тепер:

- frontend вимикає кнопку апскейлу, якщо список моделей порожній;
- backend повторно перевіряє, що вибрана модель присутня серед моделей для вибраного scale factor;
- помилка доступності моделі повертається як повідомлення, а не як мовчазний fallback.

Frontend-перевірка не вважається достатньою для безпеки стану, оскільки API pywebview можна викликати незалежно від стану кнопки.

### Робота з аудіо

Покадровий worker спочатку створює silent video. Якщо доступний FFmpeg, відеопотік з результату об'єднується з аудіопотоком оригіналу без повторного кодування відео (`-c:v copy`), а аудіо кодується в AAC. Якщо FFmpeg недоступний, зберігається silent output. Цей компроміс зберігає сумісність, але має бути окремо перевірений на цільовій системі.

### Відомі обмеження та наступні кроки

- Тимчасові файли прив'язані до lifetime history entry. Потрібно додати загальне прибирання залишкових managed-файлів під час завершення застосунку.
- Копіювання під час Export не перекодовує відео, тому операція швидка, але потребує вільного місця для другої копії.
- Для дуже довгих відео варто додати оцінку вільного місця перед запуском та явне відображення шляху/розміру тимчасового результату.
- Потрібно перевірити переривання FFmpeg і очищення частково створеного output-файлу після помилки.
- Для вимірювання оптимізацій слід фіксувати FPS, загальний час, кількість кадрів, розмір input/output, використаний scale factor, tile size та модель.

## 2026-11-13: realtime-відтворення, seek-кеш і моделі

### Realtime-відтворення

Realtime-апскейл перенесено до панелі керування відтворенням. FX-перемикач і вибір realtime-моделі тепер розташовані поруч із Play/seek, а запуск FX не запускає відео автоматично.

Play/Pause керують станом realtime-процесора: при паузі режим залишається увімкненим, але обробка призупиняється. Після Play обробка продовжується з поточної позиції.

### Seek і кеш кадрів

Кнопки перемотування, покадрової навігації та timeline передають явний seek до realtime-процесора. Оброблені JPEG-кадри кешуються через LRU-кеш.

- кеш ідентифікується відеофайлом, моделлю, scale factor та вихідним розміром;
- кеш зберігається між повторними запусками realtime у межах сесії;
- ліміт кешу — 300 секунд відео та 256 MB;
- для кадру, якого немає в кеші, показується `Upscaling frame`;
- після seek обробка продовжується від потрібного кадру.

### Моделі та точність

До `weights/` додано Real-ESRGAN x2, x4 та x4 Anime checkpoints, які конвертуються скриптом `scripts/export_onnx.py` у FP16 і FP32 ONNX. FP16 та FP32 навмисно відображаються як окремі моделі, оскільки мають різне споживання пам'яті та продуктивність.

Моделі розкладаються за scale factor у `weights/2x` і `weights/4x`, а realtime-моделі OpenCV залишаються у `weights/realtime`. Backend шукає ONNX-рекурсивно та передає runtime саме файл, вибраний користувачем.

## 2026-11-16: дослідження ComfyUI-AMD-Video-Upscaler

### Запит і правило журналювання

Користувач попросив записувати в цей журнал усі спостереження та дані, про які він питає або які досліджуються під час роботи над відеоапскейлом. Надалі результати досліджень, перевірок середовища, технічні рішення та вимірювання, що стосуються цієї функціональності, слід додавати датованими записами до цього файлу.

### Технологія

`Yasei-no-otoko/ComfyUI-AMD-Video-Upscaler` — це ComfyUI custom node, який програмно використовує AMD Advanced Media Framework (AMF) через публічні FFmpeg-фільтри `sr_amf` і `vpp_amf`. Він не викликає приватний перемикач Radeon Software для Video Upscaling і не є окремою Python-нейромережею з власними вагами.

Підтримувані алгоритми AMF включають:

- `sr1-0` — Video SR 1.0, консервативний варіант;
- `sr1-1` — Video SR 1.1, потребує перевірки сумісності драйвера;
- `bicubic`, `bilinear`, `point` — алгоритми масштабування AMF.

Сумісний node приймає RGB image tensors, але сам backend передає дані через FFmpeg subprocess. У документації проєкту зазначено обмеження: 8-bit RGB/NV12 шлях, без alpha-каналу, не zero-copy, залежність від GPU, драйвера та конкретної збірки FFmpeg.

Джерела:

- <https://github.com/Yasei-no-otoko/ComfyUI-AMD-Video-Upscaler>
- <https://gpuopen.com/advanced-media-framework/>
- <https://github.com/GPUOpen-LibrariesAndSDKs/AMF/wiki/GPU%20and%20APU%20HW%20Features%20and%20Support>

### Перевірка локального середовища

Під час перевірки 2026-11-16 виявлено:

- GPU: `AMD Radeon RX 6700 XT`;
- драйвер: `32.0.21043.12001`;
- `ffmpeg.exe` не знайдений у системному `PATH`;
- локальна програма вже має `onnxruntime-directml`, PyTorch і OpenCV;
- realtime-апскейлер у `core/services/realtime_video.py` зараз використовує OpenCV `dnn_superres`, а не AMF;
- повний відеоапскейл у `core/application_modules/media.py` працює через `VideoCapture`, Real-ESRGAN ONNX/DirectML або CPU та `VideoWriter`.

Наявність RX 6700 XT сама по собі не підтверджує доступність `sr_amf` або `sr1-1`. Потрібна практична перевірка конкретного драйвера і FFmpeg.

### Перевірка, необхідна перед інтеграцією

Після встановлення FFmpeg зі збірки, скомпільованої з AMF, потрібно виконати:

```powershell

ffmpeg -hide_banner -hwaccels | Select-String -Pattern "^amf$"
```

Очікувані результати — фільтри `sr_amf`, `vpp_amf` та hardware acceleration backend `amf`. Відсутність будь-якого з них означає, що AMD VideoSR backend не готовий до використання.

### Висновок щодо інтеграції

Найменш ризиковий варіант — додати AMF як окремий backend для повного відеоапскейлу, залишивши Real-ESRGAN ONNX/DirectML як альтернативу. У поточну realtime-архітектуру не слід запускати новий FFmpeg subprocess для кожного кадру: це створить значні накладні витрати. Realtime AMF потребував би довгоживучого FFmpeg pipeline або pipe.

Рекомендований порядок:

1. встановити та перевірити FFmpeg з AMF;
2. додати diagnostics для FFmpeg/AMF;
3. реалізувати окремий AMF video worker із передачею прогресу, помилок, скасуванням і очищенням неповного output;
4. підключити його до `start_video_upscale`;
5. порівняти на RX 6700 XT FPS, час обробки, якість і використання GPU з Real-ESRGAN;
6. лише після вимірювань розглядати realtime AMF preview.

Python-залежність для базової інтеграції не потрібна: backend можна викликати через FFmpeg subprocess.

### Діагностика

- `ffmpeg.exe` і `ffprobe.exe` відсутні в системному `PATH`;
- код у `core/application_modules/media.py` у такому випадку використовував OpenCV `VideoWriter` з кодеком `mp4v` і перейменовував silent MP4 у фінальний output;

Для коректного повторного тесту потрібно встановити FFmpeg зі штатними H.264/AAC encoder-ами та додати його `bin` до `PATH`. Після цього слід перевірити результат через `ffprobe` і відтворити його у вбудованому video element.

Готовність MSE скориговано: тепер `HAVE_ENOUGH_DATA` приймається як альтернативний критерій до 0.3 с buffered lead; додано перевірку на `canplaythrough`. JS syntax check, `git diff --check` і focused Node-перевірка fallback успішні. Повторний запуск на GPU потрібен, щоб підтвердити відсутність timeout у застосунку.

Frontend тепер використовує безпечне значення для відсутнього `stage` та `unit`, а cancelled job у backend завжди отримує `stage="cancel"`. Це прибирає каскад toast-повідомлень і повторювані записи в логах після натискання Cancel.

## 2026-11-13: синхронізація timeline з realtime FPS

HTML-відео відтворювало власний `currentTime` зі швидкістю вхідного відео, навіть коли realtime-апскейлер не встигав обробляти кадри. Через це timeline доходив до кінця раніше, ніж realtime-зображення.

Під час realtime timeline тепер використовує фактичну позицію останнього обробленого кадру. Обробник не може перевищити FPS вхідного відео, а Play/Pause realtime-контролює саме процесор, а не лише прихований HTML video element.

### Початкове realtime-прев'ю

Після запуску realtime frontend може одразу встановити паузу, якщо відео до цього не відтворювалося. Процесор тепер все одно завершує перший кадр під час початкової паузи, тому canvas отримує готове прев'ю, а подальша обробка залишається призупиненою.

## 2026-11-13: коректна realtime-перемотка

Кнопки rewind, forward і покадрової навігації використовували `videoPlayer.currentTime`, хоча під час realtime цей прихований HTML video element не є джерелом поточної позиції. Через це перемотка повторно виконувалась від застарілого часу, а timeline міг використовувати неправильну тривалість.

Усі realtime-контроли тепер беруть позицію з `realtime_position`, тривалість із стану відео та передають саме її до `seek_video_realtime`. Це також виправляє старт realtime після попередньої перемотки, збереження поточного кадру та crop у realtime-режимі.

## 2026-11-13: операції з відображуваним realtime-кадром

Збереження поточного кадру та вирізання відеокадру більше не читають безумовно сирий кадр із відеофайлу. Якщо realtime-процесор уже має JPEG, операція використовує саме цей останній відображуваний upscaled-кадр; якщо він ще не готовий, використовується звичайний source-frame як резервний варіант.

Під час перемикання елементів історії realtime-процесор попереднього елемента тепер ставиться на паузу зі збереженням stream, позиції та кешу. Це не дозволяє старому realtime-відео продовжувати обробку після вибору іншого елемента й дає змогу повернутися до того самого кадру.

## 2026-11-13: очищення realtime loading overlay

Після перемикання з відео на image-елемент історії realtime loading overlay міг залишатися видимим, оскільки його стан скидався лише у video-гілці `applyPreview`. Overlay тепер явно ховається під час відображення будь-якого image-елемента.

Якщо користувач перемикає history-елемент під час realtime, preview тепер очищається негайно: звичайне відео ставиться на паузу, MJPEG preview приховується, а loading overlay ховається ще до відповіді backend. На backend усі realtime-процесори ставляться на паузу, щоб жодне відео не продовжувало обробку після перемикання.

Перед вибором history-елемента, збереженням кадру або crop frontend спочатку передає backend поточну позицію звичайного відео або встановлює паузу realtime. Тому кожен відеоелемент повертається до часу й кадру, на яких відбулася зміна історії.

Та сама синхронізація виконується перед імпортом нового файлу та видаленням поточного елемента, тому будь-яка зміна історії спочатку фіксує позиції відео й ставить realtime-обробку на паузу.

## 2026-11-13: перемикання realtime без зміни відтворення

При ввімкненні realtime приховане HTML-відео тепер одразу ставиться на паузу, а процесор запускається з тієї самої позиції. При вимкненні позиція realtime-процесора переноситься в history entry, після чого HTML-відео отримує цей самий час.

Стан Play/Pause також зберігається: пауза залишається паузою, а активне відтворення відновлюється після завершення перемикання. На canvas змінюється лише джерело/роздільна здатність кадру, без фонового відтворення оригінального відео.

Для точного збігу кадру і timeline старт realtime та seek використовують номер кадру (`CAP_PROP_POS_FRAMES`), а не приблизний час декодера. При вимкненні realtime backend повертає фактичну позицію останнього обробленого кадру, і HTML video встановлюється саме на неї.

## 2026-11-13: realtime Play/Pause

Кнопка Play/Pause раніше перевіряла стан прихованого HTML video element. Під час realtime він залишається paused, тому повторне натискання не могло відновити або призупинити realtime-процесор.

Тепер під час realtime кнопка використовує `realtime_paused`, а для звичайного відео зберігає керування HTML video element.

## 2026-11-16: дослідження GPU для realtime-апскейлу

### Поточний шлях

`RealTimeVideoProcessor` відкриває відео через OpenCV `VideoCapture`, а `_RealtimeUpscaler` запускає OpenCV `dnn_superres` для кожного кадру. На цей момент у diagnostics жорстко вказано CPU. Застосунок уже має ONNX Runtime з `DmlExecutionProvider`, який використовується Real-ESRGAN у повному відеоапскейлі.

### Перевірені GPU backend-и

- OpenCV бачить OpenCL-пристрій AMD `gfx1031` (Advanced Micro Devices) і має OpenCL увімкненим.
- ESPCN `.pb` модель успішно повернула x2 кадр при `DNN_TARGET_OPENCL`, але під час інференсу OpenCV вивів `CL_INVALID_COMPILER_OPTIONS` для `ocl4dnn` kernel (`-cl-no-subgroup-ifp -D AMD_DEVICE`). Тому форма результату не доводить GPU execution: OpenCV може непомітно перейти на CPU.
- ONNX Runtime у поточному середовищі оголошує `DmlExecutionProvider` і `CPUExecutionProvider`.
- FFmpeg `sr_amf` вже проходив апаратний smoke test на RX 6700 XT, але AMF VideoSR є іншим алгоритмом, а не прискореним виконанням ESPCN/FSRCNN.

### Необхідне рішення перед реалізацією

Потрібно вибрати між збереженням ESPCN/FSRCNN через конвертацію/підключення ONNX Runtime DirectML та окремим AMF VideoSR backend-ом, який має підтверджене апаратне виконання, але змінює алгоритм і результат. До вибору не змінювати realtime behavior; вимірювання FPS без підтвердженого GPU execution не вважати GPU benchmark.

### AMF realtime pipe: перші невдалі спроби

Після вибору AMF протестовано передавання кадрів через FFmpeg:

- вхідні `bgr24` та `yuv420p` raw frames через stdin завершуються помилкою AMF filter `Error number -129`;
- декодований file input через `sr_amf` успішно видає один кадр у sink `null`, але filter output має піксельний формат `amf`;
- спроба конвертувати цей результат у `bgr24` або MJPEG для наявного preview завершується тим самим `-129`;
- тестовий `h264_amf` output pipeline не завершився за 90 секунд і був зупинений.

Отже, попередній smoke test із null sink доводить лише запуск фільтра, але не отримання кадрів для UI. Поточний realtime preview передає JPEG кадри через локальний MJPEG endpoint, тому AMF surfaces треба або коректно завантажувати з GPU в CPU, або змінити транспорт/рендерер на hardware video stream. До розв'язання цього interop питання AMF не можна вважати готовим realtime backend-ом.

## 2026-11-16: інтеграція AMF у realtime preview

### Розв'язання interop

Підтверджено робочий long-lived FFmpeg raw-frame pipe для поточного MJPEG preview. Потрібний filtergraph:

```text
format=nv12,hwupload,sr_amf=<width>:<height>:algorithm=sr1-0:format=nv12:keep-ratio=false:fill=false,hwdownload,format=nv12,format=rgb24
```

FFmpeg запускається з `-init_hw_device amf=amf -filter_hw_device amf`. Кадри подаються через stdin як `rgb24`, а результат читається зі stdout як `rgb24`. Pipe обробляє часткові читання/записи; AMF має затримку на один кадр, тож worker зберігає індекси очікуваних кадрів і дочитує останній результат після EOF.

### Інтеграція та перевірки

- Додано окремий режим `AMD VideoSR (AMF)` у realtime model discovery; у поточному середовищі доступні перевірені масштаби x2 та x4.
- `VideoModule.start_video_realtime` передає resolved FFmpeg шлях у `RealTimeVideoProcessor`.
- AMF апскейл відбувається на GPU; `hwdownload`, RGB/JPEG кодування та передавання через наявний MJPEG preview лишаються CPU-операціями.
- На `TEST_IMAGES/Wow Original_2025.05.23-12.57.mp4` перевірено x2 вихід 1280×720: 60 послідовних кадрів оброблено за 2.94 с (20.42 FPS), без додаткового декодування JPEG у тестовому клієнті.
- Перевірено pause/resume, seek до 1.0 с, stop без помилки, x4 вихід 2560×1440 та flush восьми кадрів наприкінці файлу.
- Перший замір показав лише 9.5 FPS. Причина — `Event.wait(0.05)` блокував цикл навіть коли pause-прапорець був вимкнений; AMF worker тепер чекає лише під час реальної паузи. Повторний замір після виправлення дав 20.42 FPS.

AMF VideoSR є окремим алгоритмом і змінює результат порівняно з ESPCN/FSRCNN. Readback на CPU означає, що pipe не zero-copy; x4 перевірений на коректність кадрів/EOF, але стабільний x4 FPS окремо не вимірювався. Масштаб x8 не перевірявся.

### Вибір фактора realtime AMF

Фактор задається через список `Output resolution`: backend формує доступні розміри як вихідна ширина/висота, помножені на factor. У поточному середовищі доступні x2 і x4; при відкритті відео за замовчуванням обирається перший доступний варіант — x2. Наприклад, для джерела 640×360 це 1280×720 або 2560×1440.

Зміна списку передається як setting `factor` і використовується для цільового розміру AMF кадру. Поки realtime запущений, список вимкнений; щоб змінити фактор, потрібно зупинити realtime, обрати іншу роздільність і запустити його знову.

## 2026-11-16: низьке GPU та високе CPU навантаження у realtime AMF

### Вимірювання

Під час активної обробки знято Windows `GPU Engine(*)\Utilization Percentage` і зіставлено engine counters з PID саме AMF-процесу FFmpeg:

- x2, вихід 1280×720: 6 послідовних семплів показали приблизно 4.1–4.3% на GPU `3D` engine; `compute` та video-codec engines — 0%. За цей період Python-процес використав близько 2.8 CPU-секунди, FFmpeg — близько 0.2 CPU-секунди.
- x4, вихід 2560×1440: середня GPU `3D` активність FFmpeg — 1.41% (максимум 1.53%), `compute` та video-codec engines — 0%. Python використав близько 5.8 CPU-секунди за приблизно 6 секунд, FFmpeg — близько 0.1 CPU-секунди.
- Профіль x4: 20 кадрів за 8.39 с (2.38 FPS); середній час JPEG encode — 49.3 мс/кадр, `send_frame` — 3.8 мс, `capture.read` — 0.7 мс, `cvtColor` — 1.1 мс. `read_frame` займав 361.6 мс wall time переважно через очікування pipe/GPU output.

### Висновок

AMF-фільтр працює через FFmpeg hardware device і FFmpeg PID має ненульову GPU `3D` активність, але це лише мала частина повного шляху. OpenCV декодує відео на CPU; Python конвертує кадри, передає raw bytes і JPEG-кодує збільшене зображення; FFmpeg виконує форматні перетворення та `hwdownload`. На x4 великі CPU-visible кадри й JPEG preview обмежують швидкість та тримають CPU зайнятим, тоді як GPU більшу частину часу очікує.

Поточний MJPEG preview не є GPU-resident/zero-copy шляхом. Просте підвищення factor не усуває цю архітектурну межу. Щоб істотно зменшити CPU та краще використати GPU, потрібно прототипувати інший preview transport/renderer, який не повертає кожен upscaled кадр у Python для JPEG-кодування. Попередній `h264_amf` smoke test зависав, тому перед зміною UI/transport потрібен окремий обмежений прототип.

## 2026-11-16: прототип AMF H.264 realtime transport

### Перевірені варіанти

- Контрольний `h264_amf` encode без `sr_amf` завершився за 0.25 с; ffprobe знайшов H.264 1280×720 з 12 кадрами, три кадри успішно декодувалися.
- Зв'язка `sr_amf → h264_amf` в одному FFmpeg процесі не завершилася за 40 с ані з прямими AMF frames, ані після явного `hwdownload`/NV12. Окремий raw-input live тест не видав fragment і був зупинений після таймауту; його завислий FFmpeg PID зупинено.
- Працює двопроцесний прототип: перший FFmpeg виконує AMF VideoSR і читає кадр назад у Python; другий приймає BGR raw frames через stdin, виконує `format=nv12,hwupload`, кодує `h264_amf` і віддає fragmented MP4 через stdout.

### Результат двопроцесного прототипу

На x2 тесті отримано 60 SR-кадрів і 60 MP4 fragments до закриття encoder input; вихідний потік — 2,749,172 bytes. ffprobe підтвердив H.264 1280×720 і 60 кадрів, FFmpeg успішно декодував три кадри. Увесь тестовий потік сформовано за 2.75 с.

### Обмеження й рішення

Це лише CLI-прототип, ще не підключений до `VideoStreamServer` чи WebView. Двопроцесний варіант усе ще передає повнорозмірні кадри через RAM і повторно завантажує їх для AMF encoder-а; вимірювання зменшення CPU та браузерного відтворення поки немає. Прямий zero-copy варіант із одним FFmpeg процесом не підтверджений через зависання, тому перед інтеграцією потрібно окремо вирішити, чи прийнятний прототипований обхід із двома процесами та CPU-переходом.

## 2026-11-16: H.264/MSE preview для realtime AMF

### Транспорт та інтеграція

Звичайний `<video src>` не відтворює fragmented MP4, який надходить частинами по HTTP (`DEMUXER_ERROR_COULD_NOT_OPEN`); той самий завершений файл відтворюється. Chromium підтримує потрібний формат через Media Source Extensions (MSE), тому додано окремий MSE preview для AMD AMF. Інші realtime-моделі залишилися на MJPEG.

AMF VideoSR і H.264 encoder працюють у двох FFmpeg процесах: спроби з'єднати їх в один процес зависали, а розділений потік проходить перевірки. Між процесами передається NV12: це прибирає зайві RGB-конвертації та JPEG-кодування кожного кадру в Python для preview, але не усуває CPU readback з AMF-процесу. H.264 використовує Main profile, level 5.0 (`avc1.4D0032`); ffprobe підтвердив level 50, Chromium підтримує цей MIME type для перевірених x2/x4 розмірів.

Додано chunked `/realtime/{token}/mp4` endpoint і MSE-контролер у UI. Черга H.264 обмежена 64 фрагментами по 64 KiB, а черга raw AMF кадрів — чотирма кадрами. Seek/reconnect створює нову stream revision; timestamp offset переносить буфер у потрібну позицію. JPEG для `latest_frame` кодується лише за запитом, зокрема коли користувач зберігає кадр.

### Перевірки та вимірювання

- Chromium відтворив x2 H.264 MSE потік у 1280×720 та x4 у 2560×1440 без decoder error.
- Фінальний x2 seek перевірено на активному потоці: відтворення з offsets 5 с і 8 с дало відповідно 5.62 с і 8.61 с, `readyState=4`, розмір 1280×720. Переривання попередніх HTTP fetch-запитів під час seek було очікуваним.
- Windows повідомляв `ConnectionAbortedError` при скасуванні старого MP4 fetch під час seek. MP4 handler тепер обробляє цей розрив як звичайне закриття клієнта; повторний тест обох seek пройшов без traceback, processor завершився з `error=null`.
- Після переходу AMF→NV12 `latest_frame` за запитом сформував коректний JPEG 1280×720.
- x2 під час п'ятисекундного семплу: Python використав 0.14 CPU-секунди, AMF FFmpeg — 0.19, H.264 FFmpeg — 0.09. Середня GPU активність AMF process: 8.92% 3D; H.264 encoder: 8.77% video-codec та 3.15% 3D. У короткому diagnostics семплі було близько 15.18 FPS.
- x4 під час п'ятисекундного семплу: Python використав 4.06 CPU-секунди, AMF FFmpeg — 0.03, H.264 FFmpeg — 0.06. Середня GPU активність AMF process: 6.35% 3D; H.264 encoder: 4.70% video-codec та 1.66% 3D. Короткий семпл показав близько 4.8 FPS, повний diagnostics — близько 7.3 FPS.

### Висновок та обмеження

H.264/MSE прибрав JPEG encode на кожен кадр та зменшив CPU-витрати, водночас підтверджено ненульову активність AMF і video-codec GPU engines. Це не zero-copy: декодування OpenCV, передавання raw кадрів та readback залишають CPU роботу; x4 усе ще займає близько 81% одного CPU ядра за виміряний інтервал і працює приблизно на 4.8–7.3 FPS. Це краще за попередній x4 MJPEG замір 2.38 FPS та 5.8 CPU-секунди за 6 секунд, але не означає, що навантаження повністю перенесено на GPU.

Перевірено реальний stream endpoint у Chromium; повний PyWebView UI end-to-end та стабільний pause/resume у видимому вікні окремо не підтверджено. Під час попередньої перевірки браузер призупиняв фонове відео, тому цей результат не можна вважати перевіркою pause/resume контролів програми.

## 2026-11-16: виправлення realtime FPS meter

FPS diagnostics раніше були накопичувальним середнім `processed_frames / elapsed_since_start`, через що значення відставало від поточної швидкості кадрів. Тепер для кожного опублікованого кадру вимірюється його час обробки монотонним годинником, а FPS оновлюється як `1 / frame_processing_seconds`. Для CPU-моделей інтервал охоплює читання кадру, кеш або upscale/JPEG encode та публікацію; для AMF час початку зберігається разом із frame index, щоб врахувати однокадрову затримку пайплайна, а вимір завершується після передачі кадру H.264 encoder-у. Очікування між кадрами не враховується.

Перевірка формули: 100 мс дали 10 FPS, 25 мс — 40 FPS. На шести перших x2 AMF кадрах отримано діагностичні значення 5.35, 10.64, 12.66, 12.82, 32.26 і 21.28 FPS без processor error. Це короткий startup семпл, не benchmark; миттєвий FPS може коливатися між кадрами, особливо під час запуску пайплайна.

Додано окреме поле `average_fps`: кількість опублікованих кадрів, поділена на час від запуску realtime-процесора. Diagnostics UI показує `Processing FPS` та накопичувальний `Average FPS` окремими рядками.

## 2026-11-18: згладжування realtime FPS

Миттєве `1 / frame_time` могло сильно змінюватися від кадру до кадру. Застосовано експоненційне згладжування часу кадру з [підходу зі Stack Overflow](https://stackoverflow.com/questions/87304/calculating-frames-per-second-in-a-game): `smoothed_time = 0.9 * previous_smoothed_time + 0.1 * current_frame_time`; відображуваний `Processing FPS` тепер дорівнює `1 / smoothed_time`. Перший кадр задає початкове значення без штучного розгону від нуля. Окремий `Average FPS` лишився загальним середнім від старту, без зміни семантики.

## 2026-11-18: видалення Average FPS

На прохання користувача прибрано рядок `Average FPS` із diagnostics UI та пов'язані невикористані backend-лічильники. Згладжений `Processing FPS` лишився єдиним показником швидкості realtime-обробки.

## 2026-11-18: окремий вибір realtime-роздільності та алгоритму

Realtime налаштування винесено в окрему секцію відеопанелі: користувач спершу обирає вихідну роздільність, потім бачить лише сумісні з нею алгоритми. Доступність factor/model pair визначається реальними realtime-вагами та AMD AMF; backend перевіряє пару при збереженні й запуску.

Realtime factor зберігається окремо від `settings.enhancement.factor`, тому вибір preview не змінює роздільність подальшого video export. У toolbar залишено лише кнопку FX; модель і роздільність вимикаються на час роботи realtime processor.

## 2026-11-19: realtime preview зависає на декодуванні першого кадру

У `app_logs/logs.txt` новий запуск AMD VideoSR x2 почався о 21:30:57 на позиції 0.016 с, після чого майже одразу backend отримав pause=true. У логах немає подій про кадри, MSE bytes, browser media error чи `loadeddata`, тож сам журнал не доводить, що завис саме OpenCV input decoder.

UI-крок `Decode first frame` відповідає очікуванню `loadeddata` у браузерному MSE element. Backend змінює loading stage на `Waiting for decoded preview frame` одразу після того, як перший апскейлений кадр записаний у stdin H.264 encoder-а; це не підтверджує, що encoder вже видав MP4 fragment або що браузер його отримав. Якщо UI лишився на кроці 5, ймовірна ділянка очікування — H.264 encoder output → HTTP/MSE append → browser decode, а не саме читання вихідного кадру OpenCV. До цього виправлення `RealtimeMsePreview` не обробляв media element `error` і не мав timeout очікування `loadeddata`, тому такі випадки могли залишати overlay без пояснення.

Попередній H.264 AMF `Init() failed with error 5` о 21:27:07 стався в іншій спробі; у новому запуску після 21:30:57 відповідної помилки не записано. У MSE controller додано 15-секундний timeout першого decoded frame, обробку HTML video `error`, ознаку невдалого старту, та лічильники отриманих/доданих MP4 байтів і chunks. Повідомлення тепер містить ці лічильники разом із `readyState`/`networkState`, а overlay ховається при помилці замість нескінченного очікування. Нуль отриманих байтів вказує на upstream encoder/HTTP відсутність output; байти, додані без `loadeddata`, звужують проблему до MSE/browser decode. Фактичний першопричинний збій на поточному користувацькому джерелі ще не відтворено.

Першопричину startup hang підтверджено на тестовому кліпі з таким самим сценарієм негайної паузи: до виправлення backend зупинився після першого AMF кадру (`sequence=1`), H.264 queue лишилася порожньою, а HTTP stream не видав байтів за 5 с. Після resume за 2 с дійшов до `sequence=62` і заповнив чергу 64 MP4 chunks. Отже, backend уважав кадр готовим одразу після запису у stdin encoder-а; пауза спрацьовувала до появи першого media fragment.

Виправлено startup gate: H.264 encoder відстежує появу першого fragmented-MP4 `moof`, а backend продовжує подавати кадри, попри початкову паузу, доки цей fragment не з'явиться. Після нього pause зберігається. Перевірка з паузою відразу після старту дала `sequence=5`, `has_encoded_frame=true`, `loading=false`, `paused=true`, `error=null`. Chromium MSE отримав 138516 bytes у 11 chunks і видав `loadeddata`; `readyState=4`, розмір 1280×720, media error відсутній. Також Node regression checks пройшли для timeout, media decoder error і успішного `loadeddata`.

## 2026-11-18: етапи підготовки AMF preview та очікування першого кадру

AMF backend позначав перший кадр готовим одразу після запису в H.264 encoder. Цей стан передавався в UI як `realtime_loading=false`, хоча browser MSE ще не встиг додати й декодувати відеокадр; тому overlay зникав раніше, ніж з'являлося зображення.

Diagnostics state тепер передає поточний етап: відкриття відео, ініціалізація AMF, апскейл першого кадру, підготовка H.264 та очікування декодованого кадру. Підготовчий panel залишається поверх чорного preview до `loadeddata` від MSE; після першого кадру він зникає. На seek/reconnect перший кадр очікується повторно.

Перевірка на live AMF x2 потоці у Chromium: backend перейшов у `Waiting for decoded preview frame`, потім реальний MSE controller отримав `loadeddata`; video мав 1280×720, `readyState=4`, відобразив 25 кадрів, sample pixel був ненульовим, media error відсутній. Так підтверджено, що backend loading завершався до готовності кадру в браузері та що перший кадр далі коректно декодується.
